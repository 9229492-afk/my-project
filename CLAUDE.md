# CLAUDE.md

Файл с контекстом проекта для Claude Code. Claude читает его автоматически в начале
каждой сессии — здесь то, что нельзя вывести из самого кода: команды, договорённости,
подводные камни.

> **Статус:** бот принимает заказы — каталог, оформление в диалоге и отправка
> заказа владельцу в личку. Корзины (несколько товаров за раз), оплаты и базы
> данных пока нет.

## Обзор проекта

`my_shop_bot` — Telegram-бот для магазина: приём заказов от покупателей прямо в чате.

**Автор проекта учится программировать.** Это влияет на то, как с ним работать:
объясняй, что делает код и зачем, а не просто выдавай готовые файлы; выбирай
понятные решения вместо «умных»; не вводи новые библиотеки и абстракции без
явной необходимости и без объяснения, какую задачу они закрывают.

Что уже работает: `/start`, `/help`, `/id`, каталог `/catalog`, карточка товара
с кнопкой «Купить», оформление заказа в диалоге (имя → телефон → адрес →
подтверждение) и отправка готового заказа владельцу магазина в личные сообщения.
`/cancel` прерывает оформление на любом шаге.

## Технологический стек

- **Python** 3.11+
- **aiogram 3.x** — фреймворк для Telegram Bot API, асинхронный
- **python-dotenv** — чтение токена и настроек из `.env`
- Хранилище данных: пока его нет. Товары лежат списком в `bot/catalog.py`.
  База (скорее всего SQLite) понадобится, когда появятся заказы.

### Важно: aiogram 3, а не 2

Большая часть гайдов и ответов в интернете написана под aiogram 2.x, и её API
несовместим с 3.x. Признаки устаревшего кода: `from aiogram import executor`,
`executor.start_polling(...)`, декораторы `@dp.message_handler(...)`,
`ParseMode` из корня пакета. В aiogram 3 вместо этого — `Router`, `Dispatcher`
с `dp.start_polling(bot)`, декораторы `@router.message(...)` и фильтры-объекты
(`Command("start")`). Если код из примера не запускается — сначала проверь версию.

## Команды

```bash
# Создать виртуальное окружение и войти в него
python3 -m venv .venv
source .venv/bin/activate

# Установить зависимости (dev — вместе с pytest и ruff)
pip install -r requirements-dev.txt

# Запустить бота
python -m bot

# Тесты
pytest                        # все
pytest tests/test_catalog.py  # один файл
pytest -k "цена"              # по имени теста

# Линтер и форматирование
ruff check .
ruff format .
```

Перед первым запуском: `cp .env.example .env` и вставить токен от @BotFather.

## Архитектура

```
bot/
  __main__.py         # точка входа: Bot, Dispatcher, подключение роутеров, polling
  config.py           # BOT_TOKEN и ADMIN_ID из .env
  catalog.py          # товары и логика каталога — без кода Telegram
  orders.py           # заказ, проверка телефона/имени/адреса, тексты — без кода Telegram
  states.py           # шаги оформления заказа (FSM)
  handlers/
    start.py          # /start, /help, /id
    catalog.py        # /catalog, нажатия на товар и «назад»
    order.py          # «Купить», диалог оформления, /cancel, отправка заказа админу
  keyboards/
    catalog.py        # кнопки каталога и карточки товара
    order.py          # кнопки подтверждения и «отправить мой номер»
tests/
  test_catalog.py     # тесты каталога
  test_orders.py      # тесты проверки данных и текстов заказа
```

Файлы для запуска вне своей машины: `Dockerfile` и `Procfile` — для хостинга,
`.devcontainer/` — чтобы GitHub Codespaces сам ставил зависимости.

Заказ уходит владельцу через `bot.send_message(config.admin_id, ...)`. `config`
попадает в обработчик потому, что передан в `Dispatcher(config=config)` — aiogram
подставляет такие значения в аргументы обработчиков по имени.

Ключевые принципы:

- Обработчики группируются в **роутеры** (`Router`) и подключаются к `Dispatcher`
  в точке входа. Один роутер — один сценарий (каталог, корзина, заказ).
- На каждое нажатие inline-кнопки обязателен `await callback.answer()`, иначе
  у пользователя крутится «часик» на кнопке до таймаута.
- `callback.message` может оказаться недоступным (старое сообщение) — перед
  `edit_text` проверяем `isinstance(callback.message, Message)`.
- `callback_data` ограничен 64 байтами. Складывать в него описания товаров нельзя,
  только короткий id.
- Многошаговые диалоги делаются через **FSM** aiogram (`bot/states.py`), а не
  через самодельные словари с состоянием пользователя.
- Бизнес-логика не живёт внутри обработчиков: обработчик принимает апдейт,
  вызывает функцию, отправляет ответ. Так логику можно тестировать без Telegram.

## Соглашения в коде

- Весь код обработчиков — `async def`, вызовы к Telegram — через `await`.
- **Никаких блокирующих вызовов** внутри `async def`: ни `time.sleep`, ни
  `requests`, ни синхронных запросов к базе. Один такой вызов останавливает
  всего бота целиком. Вместо них — `asyncio.sleep`, `aiohttp`, async-драйвер БД.
- Имена: `snake_case` для функций и переменных, `CamelCase` для классов.
- Тексты сообщений для пользователя не разбросаны по коду — выносить в отдельное
  место, когда их станет больше нескольких штук.
- Тесты лежат в `tests/`, имя файла `test_*.py`. Покрывать в первую очередь
  бизнес-логику (расчёт суммы, валидация ввода), а не обёртки над API Telegram.

## Подводные камни

- **Токен бота — это пароль.** Лежит в `.env` в переменной `BOT_TOKEN`, читается
  через `python-dotenv`. `.env` обязан быть в `.gitignore`. Если токен всё же
  попал в коммит — его недостаточно удалить из файла: он остаётся в истории git,
  нужно немедленно отозвать токен через @BotFather и выпустить новый.
- Одновременно может работать только **один** экземпляр бота на одном токене.
  Запущенный локально бот и бот на сервере будут отбирать апдейты друг у друга —
  ошибка выглядит как `TerminatedByOtherGetUpdates`.
- Telegram ограничивает частоту сообщений (примерно 30 в секунду суммарно,
  1 в секунду в один чат). При рассылках нужны паузы, иначе прилетит `RetryAfter`.
- Пользователь может заблокировать бота — отправка ему упадёт с ошибкой. Это
  нормальная ситуация, её нужно обрабатывать, а не считать сбоем.
- Для разработки используется long polling (`dp.start_polling`), вебхуки не нужны
  и требуют публичного HTTPS-адреса.
- На хостинге `.env` не существует: `BOT_TOKEN` и `ADMIN_ID` задаются переменными
  окружения. `load_dotenv()` в этом случае просто ничего не делает, и `os.getenv`
  читает их из окружения — поэтому один и тот же `config.py` работает и локально,
  и в контейнере. Тип сервиса на хостинге — worker, не web: бот не слушает HTTP.
- **Бот не может написать первым тому, кто ему не писал.** Чтобы заказы
  доходили, владелец магазина обязан один раз сам отправить боту `/start`.
  Иначе отправка падает с `TelegramForbiddenError: bot can't initiate
  conversation with a user`. Обработано: заказ в этом случае целиком пишется
  в лог, а покупателю бот говорит связаться напрямую.
- Состояния FSM хранятся в памяти процесса (`MemoryStorage` по умолчанию).
  Перезапуск бота стирает незаконченные оформления — пользователю придётся
  начать заново. Оформленные заказы это не затрагивает: они уже отправлены.
- В `ADMIN_ID` нужен числовой Telegram ID, а не `@username`. Узнать свой —
  команда `/id` у самого бота. Пустой `ADMIN_ID` намеренно не мешает запуску:
  иначе бота нельзя было бы поднять, чтобы узнать свой ID. В этом режиме заказы
  пишутся только в лог, а покупателю бот отвечает, что магазин настраивается.

## Чего делать не нужно

- Не коммитить `.env`, токен бота и любые ключи доступа.
- Не хардкодить токен в коде «на минутку» — минутка попадает в историю git.
- Не писать код под aiogram 2.x (см. раздел про версию выше).
- Не хранить заказы только в FSM: оттуда они пропадают при перезапуске.
- Не тащить в проект тяжёлые зависимости и слои абстракции, пока задача их не требует.
